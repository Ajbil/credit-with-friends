# System overview

## Stack

| Layer | Choice |
|---|---|
| Language | TypeScript everywhere |
| API | NestJS (latest stable), one deployable modular monolith |
| Data access | Prisma ORM, PostgreSQL 18 |
| Web | React (latest stable) + Vite, TanStack Router and Query, Tailwind CSS, shadcn/ui |
| Installability | Web app manifest + service worker (vite-plugin-pwa) caching the app shell only |
| API contract | OpenAPI generated by NestJS Swagger, committed; web client generated with orval |
| Tests | Vitest (unit), Supertest against real PostgreSQL (integration), Playwright (end-to-end) |
| Monorepo | pnpm workspaces + Turborepo, package scope `@symphony/` (harness `nx.md`) |

## Repository layout

```
apps/
  api/            NestJS modular monolith
    src/common/       config, logging, exception filter, auth guard, db client
    src/service-bus/  in-process request/response and events between modules
    src/modules/
      accounts/       sign-in, pending sign-ins, sessions, profile, consent, deletion
      circles/        circles, invite codes, memberships, removal blocks, admin actions
      cards/          bank list, cards
      search/         card-holder search, member card browsing, contact action
      usage/          usage events, owner usage view
    prisma/           schema and migrations
  web/            React + Vite installable web app
packages/
  shared/         shared constants and types (bank ids, limits, validation rules)
```

Modules follow `constitution/03-modular-monolith-structure.md`: no module
imports another module's internals; cross-module reads and commands go through
the in-process service bus. Example: `search` asks `circles` for the member ids
that share a circle with the requester, then asks `cards` for their cards.

## Runtime topology

```
Phone browser ──HTTPS──> yourdomain.in          Cloudflare Pages (static web app)
      │
      └──HTTPS──> api.yourdomain.in             Render Starter web service, Singapore
                        │  (private network)     NestJS API + daily cleanup schedule
                        └──> Render Postgres     Basic plan, Singapore, PostgreSQL 18
```

- The web app and API are on sibling hosts of one registrable domain, so the
  session cookie is same-site (see `12-auth-sessions-security.md`).
- One always-on API instance: no cold starts, in-memory rate limiting and an
  in-process scheduler are sufficient (decision on deviations).
- WhatsApp is reached only through `https://wa.me/<digits>?text=...` links
  opened by the member's device; the API never calls WhatsApp.

## Environments

| Environment | Where | Purpose |
|---|---|---|
| Local | Docker Compose PostgreSQL 18 + `pnpm dev` | development and tests |
| Production | Render + Cloudflare Pages | owner-only testing until launch (decision 0009), then real members |

CI (GitHub Actions) runs on every pull request: lint, typecheck, unit,
integration (PostgreSQL 18 service container), end-to-end, build, and an
OpenAPI diff check. There is no coverage threshold; every acceptance criterion
has a test.

## Deploys

- Merge to `main` deploys both apps automatically.
- API: Render builds from GitHub, runs `prisma migrate deploy` as the
  pre-deploy command, then starts the new version; a failed migration stops the
  deploy.
- Web: Cloudflare Pages builds `apps/web` and publishes it.

## Configuration

All configuration is environment variables read only by the API config module
and validated at boot; the app refuses to start when one is missing or invalid.

| Variable | Meaning |
|---|---|
| `DATABASE_URL` | Render Postgres internal connection string |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google OAuth client (production publishing status) |
| `SESSION_SECRET` | key for hashing session tokens and signing OAuth state |
| `WEB_ORIGIN` | `https://yourdomain.in`, the only CORS origin |
| `API_ORIGIN` | `https://api.yourdomain.in`, for OAuth redirect URIs |
| `OWNER_GOOGLE_ACCOUNT_ID` | the owner's stable Google account ID (usage-metrics spec); optional at boot so the owner can deploy first, read the ID on their profile, then set it before any circle is created |
| `OWNER_CONTACT_EMAIL` | contact address shown in the privacy notice and missing-bank hint |
| `LAUNCH_OPEN` | `false` until launch; while false only `PRELAUNCH_ALLOWED_EMAILS` may sign in (decision 0016) |
| `PRELAUNCH_ALLOWED_EMAILS` | comma-separated Google emails allowed before launch |
| `TEST_AUTH_ENABLED` | `true` only in local/CI tests; enables the test sign-in route |

Render and Cloudflare are configured in their dashboards (decision 0014); the
exact settings and who supplies each value live in a deployment runbook in
`docs/`, written by the deployment task.
